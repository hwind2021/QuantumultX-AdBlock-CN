# 02 · 开屏广告原理与拦截策略

理解原理，才能在规则失效时自己判断问题出在哪，而不是盲目加规则。

---

## 一、开屏广告是怎么展示出来的

一次典型的开屏广告，背后是这条链路：

```
  用户点击 App 图标
        │
        ▼
  ┌──────────────┐
  │  App 启动     │
  └──────┬───────┘
         │ ① SDK 初始化
         ▼
  ┌──────────────┐     ② 请求广告      ┌──────────────┐
  │  广告 SDK     │ ─────────────────▶ │  广告服务器   │
  │ 穿山甲/广点通 │                    │  (ADX)       │
  └──────┬───────┘ ◀───────────────── └──────────────┘
         │        ③ 返回广告配置
         │           (素材URL/展示时长/落地页)
         ▼
  ┌──────────────┐     ④ 下载素材      ┌──────────────┐
  │  渲染开屏页   │ ─────────────────▶ │  素材 CDN    │
  └──────┬───────┘                    └──────────────┘
         │ ⑤ 展示 3~5 秒（可跳过）
         ▼
  ┌──────────────┐
  │  进入主页     │
  └──────────────┘
```

**关键认知：广告是「请求—返回—渲染」三段式，每一段都是拦截点。**

---

## 二、四个拦截点，对应四种手段

| 拦截点 | 手段 | 效果 | 副作用 |
|---|---|---|---|
| **① SDK 初始化** | 分流拦截 SDK 配置域名 | SDK 降级，不请求广告 | 个别 App 可能异常 |
| **② 广告请求** | 分流 / 重写拦截 ADX 域名 | 拿不到广告，直接跳过 | 小 |
| **③ 响应解析** | JS 脚本清空响应内容 | **瞬间跳过，无等待** | 需 MITM |
| **④ 素材下载** | 分流拦截素材 CDN | 素材加载失败，多数 App 容错跳过 | 小 |

### 手段对比：REJECT 与脚本的本质差异

这是很多人搞不清、但体验差别巨大的一点。

**单纯 REJECT（分流拦截）：**

```
App: 请求广告 ──▶ ✗ 连接被拒
App: （SDK 内部等待超时 1.5~5 秒）⏳
App: 超时了，算了，进主页
```

表现为：**卡在启动页几秒**，虽然没广告，但一样烦。

**JS 脚本改写响应：**

```
App: 请求广告 ──▶ ✓ 200 OK
                  {"ad_list": [], "duration": 0}
App: 哦，这次没广告投放，直接进主页
```

表现为：**开屏一闪而过**，甚至察觉不到。

> 这就是为什么本项目除了分流规则，还要提供 `splash-killer.js` 脚本。
> 两者不冲突，建议叠加使用：分流负责「拦不住时的兜底」，脚本负责「拦住时的体验」。

## 三、为什么常规手段对开屏广告无效

| 方法 | 为什么无效 |
|---|---|
| **改 Hosts 文件** | iOS 沙盒限制，普通用户无法全局修改 |
| **AdBlock 类 Safari 插件** | 只作用于 Safari 网页，管不到 App 的网络请求 |
| **AdGuard / DNS 过滤** | 能被 HTTPDNS 绕过（见下节），且无法处理 HTTPS 内容 |
| **关闭个性化推荐** | 只是不精准投放，广告照常展示 |
| **断网启动** | 只对未预加载的广告有效，且影响正常功能 |

圈 X 之所以有效，是因为它工作在 **VPN 层（Network Extension）**，
能看到并控制设备上**所有 App 的全部网络请求**。

## 四、HTTPDNS：绕不过去的一道坎

这是国内 App 反拦截的核心手段，必须单独讲。

### 常规 DNS 解析 vs HTTPDNS

```
【常规 DNS】
App ──查询 api.ad.com──▶ 运营商 DNS ──▶ 1.2.3.4
                            ▲
                            │
                    圈 X 在这一层拦截 ✅

【HTTPDNS】
App ──HTTP 请求──▶ dns.aliyuncs.com ──▶ 直接返回 1.2.3.4
        （走 80/443 端口，伪装成普通 HTTPS 流量）
                            ▲
                            │
                  圈 X 若不拦这一层，App 就拿到了真实 IP，
                  随后直连 IP，完全绕过域名规则 ❌
```

**httpdns 查询本身是一个普通的 HTTP 请求，走的是域名 —— 所以它能被拦截。**
只要把 `dns.aliyuncs.com`、`httpdns.baidu.com` 这类域名拦掉，
App 就拿不到 IP，只能退回常规 DNS，重新落回我们的规则覆盖范围。

> 本项目的 `BlockHttpDNS.list` 覆盖 18 个 HTTPDNS 主机 + 41 个 IP 段，
> 包含阿里、百度、腾讯、京东、美团、网易、B 站、火山引擎等主流服务。
> **不装它，前面所有规则的拦截率都会打折。**

## 五、本项目的分层拦截架构

```
┌──────────────────────────────────────────────────────────┐
│ L0  BlockHttpDNS       阻断 HTTPDNS 绕过        【必装】  │
├──────────────────────────────────────────────────────────┤
│ L1  Splash-Killer      开屏广告 SDK 域名        【必装】  │
│     穿山甲 · 广点通 · 百青藤 · 快手 · 阿里妈妈           │
│     AdMob · AppLovin · Unity · ironSource ...            │
├──────────────────────────────────────────────────────────┤
│ L2  AdBlock-Lite       双源共识通用广告        【推荐】   │
│     信息流 · Banner · 弹窗 · 视频贴片                    │
├──────────────────────────────────────────────────────────┤
│ L3  重写规则           精准 URL 匹配，返回空    【MITM】  │
├──────────────────────────────────────────────────────────┤
│ L4  JS 脚本            响应体改写，瞬间跳过     【MITM】  │
└──────────────────────────────────────────────────────────┘
```

**为什么分这么多层？**

- L0 是**前提**，不是可选项
- L1 高命中、低开销，性价比最高 —— 只装它也能解决 80% 问题
- L2 扩大覆盖面，代价是规则量和误杀风险上升
- L3/L4 追求体验极致，代价是需要 MITM，且有一定耗电

## 六、拦截优先级：我们按什么标准挑域名

在 `tools/data/splash_sdk.conf` 里，每条域名都标注了优先级：

| 标记 | 类型 | 说明 | 示例 |
|---|---|---|---|
| **[A]** | 广告请求 / 竞价 API | 拦了直接无广告，**效果最强** | `tobid.pangolin-sdk-toutiao.com` |
| **[B]** | SDK 配置下发 | SDK 初始化降级 | `isub.snssdk.com` |
| **[C]** | 素材 CDN | 素材加载失败，App 容错跳过 | `pgdt.ugdtimg.com` |
| **[D]** | 曝光 / 点击上报 | 不影响展示，切断计费与画像 | `extlog.snssdk.com` |

**A 类是核心，C 类要谨慎**（素材 CDN 有时与正常业务共用）。

## 七、哪些情况拦截不了

坦诚说明局限，避免不切实际的期待：

1. **广告已预缓存** —— 部分 App 上次使用时就下载好了下次的开屏素材，
   断网也能展示。这类只能靠定期清 App 缓存缓解。

2. **广告与主业务共用域名** —— 比如某 App 的开屏广告走 `api.xxx.com/ad`，
   而该域名同时承载登录、内容加载。我们只能用**重写规则按路径精准匹配**，
   不能用分流规则按域名拦截，否则 App 会挂。

3. **响应体加密 / protobuf** —— JS 脚本无法解析加密响应，
   只能退回域名级拦截，体验上会有等待。

4. **服务端下发开关被 App 内置兜底** —— 极少数 App 拿不到广告时会展示
   自家运营位（比如"查看我的订单"卡片），这不是广告，也无法拦截。

## 八、效果自检方法

想知道规则到底拦截了什么，用圈 X 自带的**日志**功能：

1. 圈 X → 首页 → 右上角「**日志**」图标
2. 复现问题场景（打开某 App）
3. 观察日志中标红的 `REJECT` 记录

看到大量类似记录，说明规则正在工作：

```
[REJECT] HOST-SUFFIX,pangolin-sdk-toutiao.com → Splash-Killer
[REJECT] HOST,dns.aliyuncs.com → BlockHttpDNS
```

如果某 App 的广告域名没出现在日志里，说明：
- 该域名不在我们的规则库中（欢迎提 Issue 补充）
- 或者 App 通过 IP 直连（需检查 HTTPDNS 拦截是否生效）
