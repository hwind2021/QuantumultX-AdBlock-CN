# 05 · JS 脚本使用教程

JS 脚本是去开屏广告**体验最好**的方式：不做拦截，而是让 App「以为没有广告投放」，
从而瞬间跳过开屏，而不是干等 SDK 超时。

---

## 一、为什么需要脚本

回顾 [02 文档](02-开屏广告原理与拦截策略.md) 里的对比：

```
【REJECT 拦截】
请求广告 → ✗ 连接被拒 → SDK 等待超时 1.5~5 秒 → 进主页
                ↑ 这段时间你盯着启动页，一样烦

【JS 脚本改写】
请求广告 → ✓ 200 OK {"ad_list": []} → App 立即进主页
                ↑ 几乎无感知
```

脚本解决的是「等待」这个体验问题，不只是「有没有广告」。

## 二、Quantumult X 脚本基础

### 脚本类型

| 类型 | 触发时机 | 可用对象 |
|---|---|---|
| `script-request-body` | 请求发出前 | `$request` |
| `script-response-body` | 响应返回后 | `$response` |
| `script-request-header` | 请求头阶段 | `$request.headers` |
| `script-response-header` | 响应头阶段 | `$response.headers` |
| `script-echo-response` | 直接构造响应 | 无 |
| `cron`（定时任务） | 按计划执行 | 无 |

**去广告主要用 `script-response-body`。**

### 核心 API

```js
// 请求对象（script-request-* 可用）
$request.url          // 完整 URL
$request.method       // GET / POST ...
$request.headers      // 请求头对象
$request.body         // 请求体字符串

// 响应对象（script-response-* 可用）
$response.status      // HTTP 状态码
$response.headers     // 响应头对象
$response.body        // 响应体字符串

// 完成回调 —— 必须调用，否则请求会挂起
$done({})                          // 不对响应做改动
$done({ body: "新内容" })          // 替换响应体
$done({ response: { status: 200, headers: {}, body: "..." } })  // 完整替换

// 其他
$notify(title, subtitle, message)  // 弹系统通知（调试用）
$persistentStore.write(value, key) // 持久化存储
$persistentStore.read(key)         // 读取持久化
$httpClient.get(url, callback)     // 发起网络请求
console.log(...)                   // 输出到圈 X 日志
```

### 最重要的一条规则

**任何情况下都必须调用 `$done()`。**

忘记调用会导致请求一直挂起，App 卡死。本项目的脚本都用 `try/catch` 包裹，
确保异常时也会 `$done({})` 放行。

## 三、安装本项目脚本

### 步骤

1. 打开 [`quantumultx/script/splash-killer.js`](../quantumultx/script/splash-killer.js)
2. 全选复制
3. 圈 X → 「**脚本**」→ 右上角 `+` → 「**新建脚本**」
4. 名称填 `splash-killer`（**注意：名称要与重写规则里引用的文件名一致**）
5. 粘贴内容 → 保存

同样方式安装 `feed-killer.js`。

### 让重写规则引用本地脚本

`AdBlock-Script.conf` 里的规则默认指向本仓库的远程地址：

```
^https?:\/\/app\.bilibili\.com\/x\/v2\/splash\/list url script-response-body https://raw.githubusercontent.com/.../startup.js
```

改用本地脚本，把 URL 部分替换成脚本名：

```
^https?:\/\/app\.bilibili\.com\/x\/v2\/splash\/list url script-response-body splash-killer.js
```

**本地脚本的优势**：不依赖网络，加载更快，且不受仓库变动影响。

## 四、splash-killer.js 工作机制

### 双模式设计

```js
const CONFIG = {
    splashUrl: /splash|launch|startup|start[_-]?ad|boot[_-]?ad|开屏/i,
    ...
};
```

**模式一 · 激进模式**

当 URL 命中开屏特征（`/splash/`、`/launch/`、`/startup` 等）时，
清空响应中所有承载广告的容器字段（`data` / `list` / `result` / `ad_list` …）。

适用于：整个接口就是为开屏广告服务的（如 B 站的 `/x/v2/splash/list`）。

**模式二 · 精确模式**

URL 无明显特征时，递归遍历 JSON，只清空**键名命中广告特征**的字段：

```js
adKey: /^(ad|ads|advert|adInfo|adList|splashAd|launchAd|banner|popup|material|creative)...$/i
```

适用于：广告混在正常业务响应里（如首页数据里夹带一个 `bannerList`）。

### 处理流程

```
收到响应
   │
   ├─ 不是字符串？ ──▶ 放行（图片/protobuf 无法安全改写）
   │
   ├─ JSON 解析失败？ ─▶ 放行（HTML/加密内容）
   │
   ├─ 精确模式：递归清理广告键
   │
   ├─ URL 命中开屏特征？ ─▶ 追加激进清理
   │
   ├─ 有改动？ ─▶ 返回新响应
   │
   └─ 无改动 ─▶ 原样放行
```

### 安全设计

三层兜底，确保不会因为脚本出错导致 App 打不开：

1. **非 JSON 直接放行** —— 不尝试解析图片、protobuf、加密内容
2. **状态字段保留** —— `code` / `status` / `success` 等不改动，避免 App 判定为接口异常
3. **异常捕获** —— 整个主流程包在 `try/catch` 里，出错则原样放行

## 五、feed-killer.js 工作机制

信息流广告的挑战在于**混在真实内容里**，不能整体清空。

### 逐条甄别

```js
function isAdItem(item) {
    // 规则一：布尔标记  isAd: true
    // 规则二：类型字段  type: "ad" / cardType: "advert"
    // 规则三：广告专有多字段（adId + clickUrl + impressionUrl 同时出现 ≥2 个）
    // 规则四：键名高度广告化且字段数 ≤10
}
```

### 摘除策略

```js
const ratio = adCount / value.length;
if (ratio >= 0.9) {
    node[key] = [];                        // 九成是广告 → 整体清空
} else {
    node[key] = value.filter(x => !isAdItem(x));   // 逐条剔除，保留正常内容
}
```

这个「90% 阈值」的设计是为了区分两种情况：
- 专门的广告列表接口 → 整体清空
- 混合内容列表 → 只摘广告条目

## 六、调试技巧

### 开启调试模式

把脚本顶部的 `debug` 改为 `true`：

```js
const CONFIG = {
    debug: true,
    ...
};
```

命中规则时会弹出系统通知，显示被处理的 URL。

> 调试完成后建议改回 `false`，否则会频繁弹通知。

### 查看日志输出

脚本里的 `console.log()` 会输出到圈 X 日志：

```
圈 X → 首页 → 右上角日志图标 → 筛选脚本输出
```

### 常见问题排查

| 现象 | 原因 | 解决 |
|---|---|---|
| 脚本完全没触发 | 重写规则未引用 / 域名不在 MITM | 检查重写规则和 hostname |
| 触发了但广告还在 | 响应结构未被识别 | 抓包看真实 JSON，补充关键词 |
| App 打不开 | 脚本破坏了必要字段 | 检查 `preserveKey` 是否覆盖了该字段 |
| 请求一直转圈 | 脚本未调用 `$done()` | 检查是否有未捕获异常 |

## 七、写自己的脚本

### 最小模板

```js
// 一个最简单的响应改写脚本
const body = $response.body;

if (!body) {
    $done({});
} else {
    try {
        let obj = JSON.parse(body);
        // 在这里修改 obj
        obj.data = {};
        $done({ body: JSON.stringify(obj) });
    } catch (e) {
        $done({});   // 解析失败就放行
    }
}
```

### 建议的最佳实践

**1. 总是用 try/catch 包裹**

```js
try {
    main();
} catch (e) {
    $done({});
}
```

**2. 尽早 return，减少嵌套**

**3. 保留状态字段**

每个 App 的"成功"标识不同，常见的有：
`code: 0`、`success: true`、`status: "ok"`、`errno: 0`

误改这些字段会让 App 认为请求失败，可能触发重试或错误提示。

**4. 不要动响应头**

除非你明确知道在做什么。改 `Content-Type` 之类容易导致解析失败。

**5. 加调试开关**

方便日后排查，也方便别人使用你的脚本。
