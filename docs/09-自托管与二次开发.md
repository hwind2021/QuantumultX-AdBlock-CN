# 09 · 自托管与二次开发

如果你不想依赖 GitHub、想换数据源、或者想为项目贡献代码，看这篇。

---

## 一、本地运行构建

### 环境要求

- Python 3.9 或更高（无第三方依赖，纯标准库）
- 能访问 GitHub 的网络环境

### 基本用法

```bash
# 完整构建（拉取上游 + 生成全部产物）
python tools/build.py

# 只用本地缓存重新构建（不联网，适合反复调试）
python tools/build.py --no-fetch

# 只构建指定档位
python tools/build.py --tier splash        # 只生成开屏专项
python tools/build.py --tier splash,lite   # 开屏 + 精简版
python tools/build.py --tier rewrite       # 只生成重写规则
```

可选档位：`splash` / `lite` / `full` / `rewrite` / `optional`

### 运行校验

```bash
python tools/verify.py
```

返回 0 表示通过，非 0 表示发现安全问题（会阻断自动提交）。

### 完整流程

```bash
git clone https://github.com/hwind2021/QuantumultX-AdBlock-CN.git
cd QuantumultX-AdBlock-CN
python tools/build.py && python tools/verify.py
```

产物会生成在 `quantumultx/` 目录下。

## 二、项目结构与数据流

```
tools/
├── build.py             构建引擎
├── verify.py            安全校验器
└── data/
    ├── splash_sdk.conf  ★ 开屏 SDK 精选清单（核心资产，人工维护）
    └── whitelist.txt    关键业务白名单（人工维护）

                    ┌──────────────────┐
   上游 8 个源 ───▶ │   归一化 Rule     │
                    │  白名单过滤       │
   splash_sdk ────▶ │  去重压缩         │ ──▶ quantumultx/filter/*.list
   whitelist ─────▶ │  分级输出         │ ──▶ quantumultx/rewrite/*.conf
                    └──────────────────┘ ──▶ quantumultx/mitm/MITM.list
                              │
                              ▼
                      verify.py 安全校验
```

### 数据流说明

1. **抓取**：`fetch_all()` 并发下载 8 个上游源到 `.cache/upstream/`
2. **解析**：不同格式统一成内部 `Rule(rtype, value, weight)` 结构
3. **白名单**：剔除命中 `whitelist.txt` 的规则
4. **压缩**：后缀覆盖剪枝 + 关键词覆盖剪枝
5. **分级**：按档位合并不同置信度的规则集
6. **输出**：写入 `quantumultx/` 下对应目录
7. **校验**：`verify.py` 独立检查产物安全性

## 三、数据源配置

编辑 `tools/build.py` 顶部的 `SOURCES` 字典：

```python
SOURCES: dict[str, str] = {
    "bm7_ad_lite": "https://raw.githubusercontent.com/.../AdvertisingLite.list",
    "antiad_quanx": "https://raw.githubusercontent.com/.../anti-ad-quanx.txt",
    ...
}
```

### 添加新数据源

1. 在 `SOURCES` 中加入条目
2. 在 `build()` 里读取并解析
3. 如需特殊格式，在解析区新增一个 `parse_xxx()` 函数

### 支持的数据格式

| 格式 | 示例 | 解析函数 |
|---|---|---|
| Quantumult X | `HOST-SUFFIX,example.com,REJECT` | `parse_qx_filter()` |
| anti-AD QX | `host-suffix,example.com,reject` | `parse_antiad()` |
| 本地精选（两段式） | `HOST-SUFFIX,example.com` | `parse_curated()` |

**纯域名列表**（每行一个域名）需要先转换成 QX 格式，
可以自己加一个解析器：

```python
def parse_plain_domains(text: str, weight: int = 0) -> list[Rule]:
    rules = []
    for line in text.splitlines():
        d = line.strip().lower()
        if not d or d.startswith("#"):
            continue
        rules.append(Rule("HOST-SUFFIX", d, weight))
    return rules
```

## 四、自定义规则内容

### 添加开屏广告域名

编辑 [`tools/data/splash_sdk.conf`](../tools/data/splash_sdk.conf)。

**格式：**

```ini
# 注释以 # 开头
HOST-SUFFIX,域名          # 匹配该域名及所有子域
HOST,完整域名              # 精确匹配
HOST-KEYWORD,关键词        # 子串匹配（慎用）
```

**规范：**

1. 按 SDK 分类，写在对应注释块下
2. 标注拦截优先级 `[A]` / `[B]` / `[C]` / `[D]`
3. 优先用 `HOST-SUFFIX` 覆盖整族子域，而不是逐个写 `HOST`
4. **绝对不要**写主域后缀（如 `HOST-SUFFIX,qq.com`）

### 添加白名单

编辑 [`tools/data/whitelist.txt`](../tools/data/whitelist.txt)。

每行一个域名，匹配方式为后缀匹配：

```
example.com        # 保护 example.com 及其所有子域
```

> 带路径的条目（如 `taobao.com/h5`）会被自动忽略，仅作文档说明。

## 五、权重机制

构建时不同来源的规则带不同权重，**权重高者优先保留**：

```python
W_CURATED = 100     # 本地精选（开屏 SDK）—— 最高优先级
W_ANTIAD  = 50      # anti-AD
W_BM7     = 40      # blackmatrix7
```

当你想让某条规则"不可被覆盖"时，把它写进 `splash_sdk.conf` 即可。

### 双源共识机制

`AdBlock-Lite` 只保留**同时出现在 blackmatrix7 和 anti-AD** 的域名：

```python
consensus = antiad_set & bm7_set
```

两个独立项目都认定为广告域名，置信度显著更高，误杀风险大幅降低。

## 六、自建每日更新

### 方式一：Fork 后启用 GitHub Actions

最简单的方式：

1. Fork 本仓库
2. 仓库 Settings → Actions → General → 启用 Actions
3. 工作流会按计划自动运行

修改更新频率：编辑 `.github/workflows/daily-update.yml` 的 cron：

```yaml
schedule:
  - cron: '0 20 * * *'    # UTC 20:00 = 北京时间次日 04:00
```

> GitHub Actions 的 cron 使用 UTC 时区，且**不保证准时**，
> 高峰期可能延迟数十分钟。

### 方式二：自己的服务器 / NAS

用 cron 定时跑：

```bash
# 每天凌晨 4 点构建并推送
0 4 * * * cd /path/to/repo && python3 tools/build.py && python3 tools/verify.py && git add -A && git commit -m "chore: 每日规则更新" && git push
```

### 方式三：GitHub Actions 手动触发

仓库页面 → Actions → Run workflow

## 七、贡献指南

### 提交新的开屏广告域名

**最有价值的贡献方式。**

1. Fork 仓库
2. 编辑 `tools/data/splash_sdk.conf`
3. 本地运行 `python tools/build.py && python tools/verify.py` 验证
4. 提 PR，说明：
   - 该域名属于哪个广告 SDK
   - 在哪个 App 上验证有效
   - 拦截优先级（A/B/C/D）

### 提交误杀反馈

提 Issue，注明 App 名称、异常表现、订阅了哪些规则。
我们会把相关域名加入白名单。

### 提交脚本

放到 `quantumultx/script/` 目录，头部注释写明：
适用 App、作用、对应重写规则。

## 八、常见问题

**Q：构建时某个上游源抓取失败？**

脚本会自动回退到缓存（72 小时内）。超过 72 小时则该源被跳过，
产物规模会缩小，`verify.py` 会因"规则数低于下限"而报错阻断提交。

这是**有意设计** —— 宁可不更新，也不用残缺的规则。

**Q：为什么 `AdBlock-Full` 有 29 万条，但 `Splash-Killer` 只有 467 条？**

定位不同。`Splash-Killer` 是精挑细选的开屏 SDK 域名，
每条都针对真实投放开屏广告的服务；`Full` 是**全量合并**，
包含大量长尾广告域名、统计域名、追踪域名。

规则量与开屏拦截率不是线性关系。

**Q：能去掉某个我不需要的档位吗？**

可以。修改 `build()` 里的档位分支，或直接只运行你需要的 tier。

**Q：构建很慢怎么办？**

首次构建需要下载约 20MB 上游数据。之后用 `--no-fetch` 复用缓存，
完整构建约 1~2 分钟。
