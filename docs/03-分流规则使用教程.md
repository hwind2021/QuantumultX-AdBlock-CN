# 03 · 分流规则使用教程

分流规则（Filter）是最基础的一层，**不需要 MITM**，开销最小，也是必装的一层。

---

## 一、规则语法

Quantumult X 分流规则的基本格式：

```
类型,值,策略
```

### 四种匹配类型

| 类型 | 含义 | 匹配示例 | 开销 |
|---|---|---|---|
| `HOST` | 精确匹配完整域名 | `HOST,isub.snssdk.com` 只匹配这一个 | 最低 |
| `HOST-SUFFIX` | 后缀匹配（含自身及所有子域） | `HOST-SUFFIX,pangle.cn` 匹配 `tobid.pangle.cn`、`a.b.pangle.cn` | 低 |
| `HOST-KEYWORD` | 子串匹配 | `HOST-KEYWORD,adsdk` 匹配任何含 `adsdk` 的域名 | **最高** |
| `IP-CIDR` | IP 段匹配 | `IP-CIDR,203.107.1.0/24` | 低 |

> **性能提示**：`HOST-KEYWORD` 需要对每个域名做子串扫描，规则多了会明显拖慢
> 首次解析。本项目把它限制在 29 条高置信度关键词内，就是这个原因。

### 五种拒绝策略

| 策略 | 行为 | 适用场景 |
|---|---|---|
| `REJECT` | 直接断开连接 | **默认，开屏广告首选** |
| `REJECT-TINYGIF` | 返回 1×1 透明 GIF | 图片类广告，避免 App 报错 |
| `REJECT-NO-DROP` | 返回空但不断开 | 少数 App 需要"有响应"才不重试 |
| `REJECT-DROP` | 静默丢弃 | 避免触发 App 的重试逻辑 |
| `PROXY` / `DIRECT` | 走代理 / 直连 | 非广告用途 |

**本项目全部使用 `REJECT`。** 如果你发现某个 App 在被拦截后反复重试请求
（表现为启动变慢、流量异常），可以针对该域名改用 `REJECT-DROP`。

## 二、规则文件的结构

打开任意 `.list` 文件，你会看到这样的头部：

```
# NAME: Splash-Killer
# AUTHOR: QuantumultX-CN
# REPO: https://github.com/hwind2021/QuantumultX-AdBlock-CN
# UPDATED: 2026-09-04 18:54:55 (UTC+8)
# POLICY: REJECT
# HOST: 55
# HOST-SUFFIX: 383
# HOST-KEYWORD: 29
# TOTAL: 467
# DESC: 开屏广告专项：覆盖穿山甲/广点通/百青藤/快手/阿里妈妈/AdMob/AppLovin 等主流 SDK

HOST-SUFFIX,pangolin-sdk-toutiao.com,REJECT
...
```

头部是元信息，`#` 开头，圈 X 会自动忽略。
**看 `UPDATED` 字段可以确认你用的是不是最新版。**

## 三、订阅方式

### 方式一：远程订阅（推荐）

见 [01-快速上手](01-快速上手.md)。优点是可以自动跟随本项目每日更新。

### 方式二：本地导入

1. 把 `.list` 文件下载到手机
2. 圈 X → 配置文件 → `+` → 「**本地文件**」
3. 选择文件

缺点是需要手动更新。

### 方式三：配置文件内引用

在圈 X 的完整配置文件（`.conf`）中直接写：

```
[filter_remote]
https://raw.githubusercontent.com/hwind2021/QuantumultX-AdBlock-CN/main/quantumultx/filter/Splash-Killer.list, tag=开屏广告, enabled=true
```

`tag` 是显示在分流列表里的名字，`enabled` 控制开关。

完整示例见 [`quantumultx/conf/sample.conf`](../quantumultx/conf/sample.conf)。

## 四、按需裁剪：不是所有规则都适合你

### 场景一：设备较老，在意续航

**只装** `Splash-Killer.list` + `BlockHttpDNS.list`，共约 530 条。
开销几乎可以忽略，能解决大部分开屏广告。

### 场景二：想干净，但设备一般

装 `Splash-Killer` + `BlockHttpDNS` + `AdBlock-Lite`，共约 2.3 万条。
这是**推荐的大众配置**，在效果与开销之间取得了平衡。

### 场景三：追求极致拦截率

用 `AdBlock-Full.list`（约 29 万条）替代 Lite。

> ⚠️ 29 万条规则在 iOS 上会占用可观内存，并显著增加首次解析耗时。
> 只有在你确实需要且设备性能足够时才用。如果出现明显的网络延迟，请退回 Lite。

### 场景四：只想要隐私，不在乎广告

单独订阅 `AdBlock-Privacy.list`（约 4 万条）。

> 注意：拦截统计上报会让部分 App 的崩溃日志无法上传，
> 也会影响开发者收到反馈。**请酌情使用。**

## 五、自定义规则

### 添加自己的规则

1. 圈 X → 配置文件 → `+` → 「**本地文件**」→ 新建一个 `.list`
2. 写入你的规则，例如屏蔽某个具体 App 的广告域名：

```
# 我的自定义规则
HOST-SUFFIX,ad.example.com,REJECT
HOST,tracker.example.org,REJECT
```

3. 保存后在「分流」中启用

### 临时放行某个域名（白名单）

当你发现某 App 因为规则而功能异常，需要为它开个口子时，
圈 X **没有内置的白名单机制**，但有变通办法：

**方法：利用规则优先级**

圈 X 的分流规则**从上到下匹配，命中即停止**。
所以把放行规则放在**最前面**即可：

```
# 放行规则放第一行（策略用 DIRECT 而不是 REJECT）
HOST-SUFFIX,api.example.com,DIRECT

# 后面是你的拦截规则
HOST-SUFFIX,ad.example.com,REJECT
```

创建一个本地 `.list`，第一行写放行规则，然后在「分流」里把它
**拖到拦截规则的上面**。

## 六、找出某个 App 的广告域名

这是进阶玩法，也是为本项目贡献规则的方式。

### 步骤

1. 圈 X → 「**设置**」→ 打开「**记录网络活动**」
2. 彻底杀掉目标 App，重新打开
3. 圈 X → 首页 → 右上角日志图标
4. 观察启动瞬间产生的大量请求

### 识别技巧

开屏广告的域名通常有这些特征：

| 特征 | 例子 |
|---|---|
| 域名含广告关键词 | `pangolin`、`gdt`、`mobads`、`tanx`、`adservice` |
| 启动瞬间集中爆发 | 打开 App 的头 1 秒内密集出现 |
| 请求路径含广告语义 | `/splash`、`/launch`、`/ad/list`、`/getAd` |
| 来自知名 SDK | 对照 [02 文档](02-开屏广告原理与拦截策略.md) 的 SDK 清单 |

### 验证

把可疑域名加入自定义规则，重启 App 看广告是否消失。
确认有效后，欢迎提 PR 补充到
[`tools/data/splash_sdk.conf`](../tools/data/splash_sdk.conf)。

## 七、规则冲突与优先级

### 圈 X 的匹配顺序

```
1. 按「分流」列表从上到下的顺序，逐条检查每个规则文件
2. 在同一文件内，按行从上到下检查
3. 命中第一条即应用其策略，不再继续
```

**所以顺序很重要。** 一般原则是：

```
放行规则 / 精确规则  ← 放上面
      ↓
  宽泛广告规则       ← 放下面
```

### 本项目的规则顺序建议

```
① 自定义放行（如有）
② Splash-Killer
③ BlockHttpDNS
④ AdBlock-Lite
⑤ 其他（Privacy / AntiHijack）
```

## 八、常见问题

**Q：为什么 `AdBlock-Lite` 比 `Splash-Killer` 大这么多，但开屏效果没提升多少？**

因为它们定位不同。`Splash-Killer` 是**精挑细选的 467 条**，
每条都针对真实投放开屏广告的 SDK；`AdBlock-Lite` 里另外 2.2 万条
主要管的是**信息流、banner、弹窗**，对开屏帮助不大，但对整体体验提升明显。

**Q：规则是不是越多越好？**

不是。规则量与实际拦截率**不是线性关系**。
从 0 到 500 条（覆盖主流 SDK）提升巨大；
从 500 到 2 万条提升有限；
从 2 万到 29 万条提升可能只有几个百分点，却要付出明显的性能代价。

**Q：能同时订阅 Lite 和 Full 吗？**

能，但没意义 —— Full 已包含 Lite 的全部内容，重复匹配只是浪费性能。
