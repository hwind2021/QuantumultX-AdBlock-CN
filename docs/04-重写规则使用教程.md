# 04 · 重写规则使用教程

重写规则（Rewrite）工作在 HTTPS 解密之后，能**按 URL 精准匹配**，
是分流规则做不到的精细活。代价是必须开启 MITM。

---

## 一、什么时候需要重写规则

| 场景 | 分流规则够吗 | 说明 |
|---|---|---|
| 广告有独立域名 | ✅ 够 | 直接拦域名即可 |
| 广告与业务共用域名 | ❌ 不够 | **必须用重写按路径精准匹配** |
| 想让开屏瞬间跳过 | ❌ 不够 | 需要重写 + JS 脚本 |
| 想清理信息流里的单条广告 | ❌ 不够 | 需要重写 + 脚本 |

> 判断标准很简单：**如果广告域名和正常业务域名是同一个，分流规则就无能为力。**

---

## 二、语法详解

### 基本格式

```
正则匹配URL  类型  动作
```

三个字段用空格分隔，实际使用中正则部分通常需要转义。

### 动作类型一览

| 动作 | 返回内容 | 适用 |
|---|---|---|
| `reject` | 断开连接 | 通用 |
| `reject-200` | 200 空响应 | 通用 |
| `reject-img` | 1×1 透明 GIF | 图片广告 |
| `reject-dict` | 空 JSON 对象 `{}` | 期望对象的接口 |
| `reject-array` | 空 JSON 数组 `[]` | 期望列表的接口 |
| `reject-tinygif` | 极小 GIF | 图片广告 |
| `script-response-body` | 交给 JS 处理 | 复杂响应 |
| `script-request-body` | 交给 JS 处理请求 | 需要改请求 |

**怎么知道该用 `reject-dict` 还是 `reject-array`？**

看这个接口正常情况下返回什么。如果返回 `{...}` 用 dict，
如果返回 `[...]` 用 array。选错了 App 可能解析失败。

不确定就用 `reject-200`（返回空），多数 App 会容错跳过。

### hostname 段语法

Quantumult X 支持在重写规则文件中用 `hostname` 段限定作用域：

```
hostname = app.bilibili.com, api.zhihu.com

^https?:\/\/app\.bilibili\.com\/x\/v2\/splash\/list url reject-array
```

这样正则只需写路径部分，可读性更好。**本项目两种写法都支持。**

## 三、实例讲解

### 例 1：拦截穿山甲广告请求

```
^https?:\/\/(api-access|api5-access|tobid|isub|pangolin)\.pangolin-sdk-toutiao\.com\/ url reject-dict
```

拆解：

```
^https?:\/\/              匹配 http:// 或 https:// 开头
(api-access|api5-access|tobid|isub|pangolin)    任意一个子域
\.pangolin-sdk-toutiao\.com                      主域（点号需转义）
\/                        路径分隔符
                          
url reject-dict           URL 类型匹配，返回空 JSON 对象
```

### 例 2：通用开屏路径特征

```
(?i)\/splash\/(get|list|listAll|config|ad) url reject-dict
```

```
(?i)          忽略大小写
\/splash\/    路径含 /splash/
(get|list|listAll|config|ad)    后接这几个词之一
```

这条不限制域名，**对所有含 `/splash/xxx` 的路径生效** —— 覆盖面广，
但要小心误伤（有些 App 的启动配置接口也叫 splash）。

### 例 3：调用 JS 脚本

```
^https?:\/\/app\.bilibili\.com\/x\/v2\/splash\/list url script-response-body splash-killer.js
```

把响应交给 `splash-killer.js` 处理，脚本清空广告内容后返回。

## 四、本项目的重写规则文件

| 文件 | 条数 | 内容 |
|---|---|---|
| `AdBlock-Splash.conf` | ~112 | 开屏广告：SDK 域名 + 通用开屏路径特征 |
| `AdBlock-Feed.conf` | ~108 | 信息流 / Banner / 弹窗 |
| `AdBlock-Script.conf` | ~36 | 依赖 JS 脚本的高级拦截 |
| `AdBlock-All.conf` | ~256 | 以上合集 |

### Splash 与 Feed 的分工

```
AdBlock-Splash.conf   →  只在 App 启动时触发，管开屏
AdBlock-Feed.conf     →   App 使用全程都可能触发，管内容流
```

两者不重叠，可以同时订阅。

## 五、订阅与配置

### 订阅步骤

1. 圈 X → 配置文件 → `+` → 远程资源
2. 类型选「**重写规则**」
3. 填入 URL（地址见 [README](../README.md)）

### 必须同时配置 MITM

重写规则依赖 HTTPS 解密。**只有在 MITM `hostname` 列表里的域名才会被解密**，
不在列表里的域名，重写规则形同虚设。

本项目提供了完整清单：[`quantumultx/mitm/MITM.list`](../quantumultx/mitm/MITM.list)

详细配置见 [06-MITM与证书配置](06-MITM与证书配置.md)。

## 六、调试方法

重写规则最容易出的问题是「正则没匹配上」，但这类问题**不会报错**，
只是静默失效。需要主动验证。

### 方法一：看圈 X 日志

1. 开启 MITM 和重写规则
2. 打开目标 App
3. 圈 X → 日志 → 查找相关域名

如果看到类似记录，说明重写生效：

```
[REWRITE] reject-dict ← https://sdk.e.qq.com/...
[REWRITE] script-response-body ← https://app.bilibili.com/x/v2/splash/list
```

**如果域名出现在日志里但没有 REWRITE 标记**，说明：
- 该域名不在 MITM hostname 列表中
- 或者正则没匹配上

### 方法二：用正则工具验证

把你的正则和真实 URL 放到 [regex101.com](https://regex101.com/) 测试。

注意：圈 X 的重写正则**需要转义斜杠**（`\/`），
在 regex101 上测试时要选择对应的转义风格，或先去掉转义符。

### 方法三：在脚本里加通知

如果用 JS 脚本，把 `CONFIG.debug` 改成 `true`，
命中时会弹系统通知：

```js
const CONFIG = {
    debug: true,   // ← 改这里
    ...
};
```

## 七、自己写重写规则

### 第一步：抓到真实的广告请求 URL

1. 圈 X 开启「记录网络活动」
2. 打开目标 App，触发广告
3. 日志里找到广告请求

### 第二步：看响应内容判断动作类型

在日志里点开该请求，查看响应体：

```json
{"code":0,"data":{"ad_list":[{"ad_id":"123","img":"..."}]}}
```

返回的是对象 → 用 `reject-dict`

```json
[{"type":"ad","id":"1"},{"type":"news","id":"2"}]
```

返回的是数组 → 用 `reject-array`

### 第三步：写正则

**不要用过于宽泛的正则。** 错误示范：

```
^https?:\/\/.* url reject          ← 会拦截所有请求，App 直接报废
^https?:\/\/api\.example\.com url reject   ← 会连业务接口一起拦
```

正确做法：精确到路径，并保留业务接口：

```
^https?:\/\/api\.example\.com\/v\d\/ad\/splash url reject-dict
```

### 第四步：测试

保存后重启 App，确认：
1. 广告消失
2. **App 功能正常**（这点容易被忽略）

## 八、注意事项

### 1. 正则要转义斜杠

圈 X 的重写规则里，`/` 要写成 `\/`。这是最常犯的错误。

```
❌ ^https://api.example.com/ad
✅ ^https?:\/\/api\.example\.com\/ad
```

### 2. 谨慎使用宽泛匹配

`(?i)\/ad\/` 这类规则会匹配到任何路径含 `/ad/` 的请求，
可能误伤业务。本项目保留了少量这类规则，因为实测收益大于风险，
但你自己加规则时要慎重。

### 3. MITM 有性能开销

只对必要的域名开启 MITM。把整个 `.com` 加进 hostname 是不可取的。

### 4. 规则顺序

与分流规则一样，**从上到下匹配，命中即停止**。
精确规则放上面，宽泛规则放下面。

## 九、常见错误

| 现象 | 原因 | 解决 |
|---|---|---|
| 重写规则完全没反应 | 未开启 MITM | 见 [06 文档](06-MITM与证书配置.md) |
| 域名没在 hostname 里 | MITM 清单不全 | 把域名加入 hostname |
| 部分生效部分不生效 | 正则未匹配 | 用 regex101 验证 |
| App 报错 / 白屏 | 响应类型不匹配 | `reject-dict` 改 `reject-array` 试试 |
| App 变卡 | MITM 域名过多 | 精简 hostname 列表 |
